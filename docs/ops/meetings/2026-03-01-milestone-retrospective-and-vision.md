### 2.2 用户旅程地图（User Journey）

**PM**：我来还原一个典型场景——用户小李，想爬小红书某个博主的笔记，推到飞书多维表格里做内容分析。

#### 阶段 1：环境搭建（摩擦度：🔴 高）

小李拿到代码，看 README，发现需要：
1. 安装 Python 3.11 + uv
2. 填写 `.env`：飞书 App ID、App Secret、Base URL、Auth Key……十几个变量
3. 首次启动时 WebUI 提示"存储模式为 CSV，请切换到 SQLite"
4. 切换后刷新页面，才真正能用数据库功能

> **Dev**：首次启动体验是目前最大的问题。用户不知道要先去配置管理切换存储模式，报错信息也不够友好——400 "数据库未配置"出现在好几个页面，用户会觉得系统坏了。

#### 阶段 2：平台登录（摩擦度：🟡 中）

小李要爬小红书，需要先登录：
1. 打开配置管理，找到 cookie 配置项
2. 手动粘贴 cookie 字符串（格式要求不明确）
3. 没有"测试登录是否有效"的 UI

> **PM**：这里有个核心体验缺口——**没有平台登录向导**。用户不知道 cookie 从哪里拿，格式是什么，是否还有效。

> **Code-Reviewer**：Playwright 模式还涉及 `browser_data` 目录的登录态持久化，这在 Docker 容器里需要正确挂载 volume，文档里没有明确说明。

#### 阶段 3：创建订阅（摩擦度：🟢 低）

小李进入订阅管理，搜索博主，点击订阅——**这一步比较顺畅**，这是我们做得最好的地方之一。

#### 阶段 4：配置 Pipeline 任务（摩擦度：🟡 中）

小李去任务调度，新建任务：
1. 选任务类型——五个选项，含义不清晰（"全流程"vs"仅采集（订阅）"区别？）
2. 配置 Pipeline 步骤——每个步骤有十几个参数，tooltip 覆盖率低
3. 飞书推送步骤需要填写 Base Token + Table ID——用户从飞书后台复制，容易填错

> **PM**：步骤类型的标签语言对非技术用户不友好。"feishu_pull"、"feishu_push_json"这些名字暴露了内部实现，应该改成"从飞书读取"、"推送到飞书"。

> **Dev**：Pipeline 配置的 JSON 序列化/反序列化已经很复杂，再加上"标题去重字段"、"JSON列展开"等高级选项，配置项膨胀了。我们需要一个分层 UI——基础/高级两个折叠层。

#### 阶段 5：执行与监控（摩擦度：🟡 中）

小李点"执行"，任务运行：
1. 可以看到实时日志——**好**
2. 但日志是纯文本流，没有结构化的步骤状态（步骤 1 ✅ 步骤 2 🔄 步骤 3 ❌）
3. 如果推飞书时触发限流，任务失败，飞书告警 webhook 发送失败消息，但没有**重试机制**
4. 失败后用户需要手动重新触发，没有"重试失败步骤"的选项

#### 阶段 6：数据核查（摩擦度：🟢 低）

数据推进飞书后，用户在飞书里看到数据——这一步没有特别大的问题。

> **Brain**：好，这张地图很清晰。三个最大的摩擦点：**首次配置体验**、**平台登录管理**、**Pipeline 配置门槛**。记录下来。

### 2.3 已知缺陷与技术债

**Dev**：我来过一遍技术层面的问题：

#### 🔴 P0 级（影响可用性）

1. **SQLite 写入锁表**：APScheduler 回调和 WebUI API 都在写 SQLite，高频操作（如每 2 秒轮询日志）会产生锁竞争。生产环境建议强制使用 MySQL/Postgres。

2. **无并发任务保护**：CrawlerManager 靠 flag 串行，但如果进程崩溃后 flag 没清除，新任务永远无法启动。需要启动时检测僵尸 flag。

3. **飞书 Token 不自动刷新**：`tenant_access_token` 有效期 2 小时，长时间运行的 Pipeline 会因 Token 过期导致中途失败，且错误信息不友好。

4. **平台登录状态无校验**：任务执行前不检查 cookie/session 是否有效，执行到一半才 fail，浪费时间。

#### 🟡 P1 级（影响体验）

5. **飞书 API 无限速**：批量写入时没有速率控制，容易触发飞书 QPS 限制（官方 5 QPS）。

6. **Pipeline 步骤失败不可恢复**：整条 pipeline 失败后没有"从失败步骤重试"功能，只能整个重跑。

7. **任务日志截断**：`log_output` 是 Text 字段，极长的日志会撑大 DB。没有日志轮转/截断策略。

8. **无健康检查 API for 任务**：`/api/health` 只检查 HTTP 服务，不检查 APScheduler 是否存活。

9. **微信采集热点依赖**：微信 CDP 模式依赖 `recv_sms.py` + 手机热点，部署到无 GUI 服务器时完全不可用，没有降级提示。

#### 🟢 P2 级（技术债）

10. **无单元测试覆盖**：核心 pipeline_steps.py（1000+ 行）没有单元测试，任何修改都有风险。

11. **前端无错误边界**：Vue 组件没有 Error Boundary，一个组件抛错会导致整页白屏。

12. **配置热重载不完整**：`SAVE_DATA_OPTION` 切换后需要手动刷新页面，部分状态缓存未清除。

13. **Secret 管理缺失**：`.env` 直接写在磁盘，服务器上没有 Vault/Secret Manager 方案，也没有 `.env` 加密建议。

**Code-Reviewer**：安全层面我补充两点：

14. **WebUI 无认证**：任何局域网内的人都能访问 WebUI，操作爬虫。生产部署到公网前必须加认证。

15. **CORS 策略过宽**：目前允许所有来源，需要在生产环境锁定。

**Researcher**：从同类工具对比来看：

> CozeDiscard、Octoparse 等商业工具都有的"登录状态可视化管理"，我们是缺失的。用户如果同时管理 3 个平台的 cookie，完全没有地方看哪个有效、哪个过期。

> **Brain**：很好，问题已经摆明了。我们来看下一部分——我们要去哪里。

## 三、议题 B：前瞻展望

### 3.1 项目愿景

> **Brain**：我想先请 PM 给项目一个定义，我们到底在做什么？

**PM**：

> **MediaCrawler WebUI 的定位是：面向内容运营团队的「多平台内容情报工作站」——让非技术人员也能定期采集、清洗多平台内容，并以结构化方式流入飞书等协作工具，服务于内容分析、竞品监控、选题决策等场景。**

### 3.2 Roadmap v2

**Brain**：我们把 v2 分三个里程碑来看：

#### 里程碑 1：生产可信赖（v1.x 补丁期，约 2-4 周）

> 目标：让部署到服务器的版本跑得住、跑得稳

| 方向 | 具体内容 |
|------|---------|
| 稳定性 | CrawlerManager 僵尸 flag 检测；飞书 Token 自动刷新；SQLite 并发写优化（WAL 模式） |
| 安全 | WebUI 基础 HTTP Basic Auth 或 Token 认证；CORS 生产配置 |
| 可观测性 | 结构化日志（步骤级状态 JSON）；任务执行统计看板 |
| 飞书限速 | 推送步骤添加 `rate_limit` 参数（默认 5 QPS），超限自动 sleep |

#### 里程碑 2：降低门槛（v2.0，约 1-2 月）

> 目标：让新用户 30 分钟内跑通第一个任务

| 方向 | 具体内容 |
|------|---------|
| 引导流程 | 首次启动向导（Setup Wizard）：检测依赖 → 选存储 → 测试飞书连接 → 创建第一个订阅 |
| 登录管理 | 平台 Session 管理页：展示各平台登录状态（有效/过期）、一键刷新 Cookie |
| Pipeline 简化 | 常用模板内置化（"订阅采集+推飞书"一键生成）；步骤参数分"基础/高级"折叠 |
| 文档 | 每个平台的 cookie 获取教程（附截图） |

#### 里程碑 3：能力扩展（v2.x，2 月以后）

> 目标：支撑更多真实业务场景

| 方向 | 具体内容 | 优先级 |
|------|---------|--------|
| 通知渠道 | 告警/任务完成通知支持企业微信机器人、钉钉 webhook | P1 |
| 数据分析 | Dashboard 增加趋势图（每日新增内容量、平台分布）、词云 | P1 |
| 增量采集 | Pipeline 支持"仅采集最新 N 条"+ 去重（基于内容 ID） | P1 |
| 多飞书账号 | 配置多个飞书 Base，任务级选择推往哪个 Base | P2 |
| 用户认证 | 多用户支持（Admin/Operator 角色）+ 操作审计 | P2 |
| 插件接口 | Pipeline 步骤可通过 Python 插件扩展（自定义处理器） | P2 |
| SaaS 化 | 多租户架构（如果有托管需求）| P3，远期 |

### 3.3 优先级矩阵

**PM**：我来画一个影响 × 代价的矩阵：

```
         代价低             代价高
影响高 │ [快赢区]          │ [战略区]
       │ • Token 自动刷新  │ • Setup Wizard
       │ • 飞书限速        │ • 登录管理页
       │ • WebUI 认证      │ • 增量采集
       │ • WAL 模式        │
───────┼───────────────────┼──────────────────
影响低 │ [填坑区]          │ [缓做区]
       │ • 日志截断        │ • 多飞书账号
       │ • 错误边界        │ • 多用户角色
       │ • CORS 配置       │ • 插件接口
```

> **Dev**：我再强调一次：**WebUI 认证是最该先做的**。不是功能优先级的问题，是安全底线。一个无认证的爬虫控制面板暴露在公网上，是非常危险的。

> **Code-Reviewer**：同意。即使是 HTTP Basic Auth 配一个 `WEBUI_USERNAME/WEBUI_PASSWORD` 环境变量，10 分钟就能做，把这个放 P0。

> **Researcher**：从用户反馈角度，Setup Wizard 会让"第一次成功"的时间从可能的小时级降到 30 分钟，这对口碑传播很关键。

## 五、Brain 闭幕总结

> 好，我来收一下。
>
> **我们做到了什么**：一个从零到可部署的完整产品骨架，8 个功能模块都能跑，Pipeline 引擎可以编排复杂的采集→清洗→推送流程，调度器能定时自动执行。这是真实可用的工程交付，不是 demo。
>
> **我们的差距在哪里**：分两层。表层是 Bug 和体验摩擦——Token 刷新、限速、日志截断、CORS，这些都是几小时的工作量；深层是产品门槛——新用户从拿到代码到跑通第一个任务，路上有太多无人引导的坑，这需要系统性的 Setup Wizard + 文档投入。
>
> **我们要去哪里**：不是 SaaS，不是插件市场，那些是远期。近期唯一的目标是：**让一个没有技术背景的内容运营同学，能在 30 分钟内独立跑通"订阅小红书博主 → 定时采集 → 推到飞书表格"这条路**。只要这条路顺畅了，所有其他功能才有意义。
>
> **下一步**：作者先把当前版本部署到服务器验证稳定性。与此同时，P0 的五件事（认证、Token 刷新、僵尸检测、WAL 模式、CORS）是最紧要的安全/稳定性补丁，建议在测试期间并行完成。
