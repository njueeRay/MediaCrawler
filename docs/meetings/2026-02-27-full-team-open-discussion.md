## 一、Brain 开场主持

> 各位，今天这次会议没有具体的交付任务，是一次开放讨论。我先抛出几个事实，供大家思考。
>
> **我们走到了哪里？** 从 fork 到现在，dev 分支 418 个文件变更、+66,608/-11,898 行代码、20 个 commit。WebUI 8 个功能模块全部基本可用，创作者搜索覆盖了 5 个平台，Pipeline 引擎可以流水线编排，部署骨架（Docker + systemd）也有了。这不是一个 demo，这已经是一个有完整前后端、有调度、有数据同步能力的产品。
>
> **但我也想诚实地说几个观察：**
> 1. 这 66,000 行增量代码全在 dev 分支，从未合并到 main，也没有 CI——这意味着我们在一个没有安全网的高速公路上开车
> 2. 用户的核心旅程「配置 → 订阅 → 定时采集 → 飞书同步 → 部署」至今没有一次完整的端到端跑通
> 3. 我们连续修了两轮 WebUI bug，每次都是用户手动测试发现的——说明我们的质量反馈循环太慢
> 4. 代码量增长很快，但文档、测试、部署这些"慢活"跟不上
>
> 今天想听听每个人的真实想法。不用客气，有问题就说。

## 二、各角色发言

### Dev（开发工程师）

**当前状态评估：**

- 后端架构我是比较满意的。FastAPI + SQLAlchemy + Pipeline 引擎分层清晰，service 层和 router 层职责分明。最近加的 `subscription_service.py` 搜索逻辑支持多平台，扩展性不错。
- 但我想坦率说一个问题：**代码里有不少"两条路径做同一件事"的情况**。最典型的就是上一轮修的 auth_key bug——测试连接从 `.env` 读、搜索从 config 模块读，两边不同步。这种模式在项目里不止一处。比如 `config/__init__.py` 的 `reload_from_env()` 和 `config_service._read_env_file()` 其实是两套独立的配置加载机制，迟早还会出问题。
- **我的建议是做一次「配置读取统一」**：所有运行时配置读取都走同一个入口（比如 config_service），而不是有的地方直接 `from config import xxx`，有的地方读 `.env` 文件。

**方向看法：**

- 用户说"跑通全流程再部署"，我认为这是对的。现在不该急着加新功能（比如快手/知乎搜索），而是应该把现有功能的端到端可靠性打磨好。
- Pipeline 引擎的 `subscription_crawl` 步骤目前只真正跑通了微信平台。小红书和抖音的 crawl 逻辑还没对接到 Pipeline 里。这是"跑通全流程"的关键缺口。

**Ideas：**

1. **Config 单一数据源原则**：引入一个 `ConfigProvider` 类，统一所有配置读取，消除 `.env 直读` vs `config 模块` 的二元性
2. **Pipeline 步骤可测试化**：每个 pipeline step 应该可以单独跑（dry-run 模式），方便用户验证配置是否正确
3. **错误可追溯**：现在很多地方 `except Exception: pass` 或者 `except Exception as e: print(...)`，需要统一用 logging + 前端错误面板

### PM（项目经理）

**当前状态评估：**

- 从项目管理角度看，我们的节奏其实很快——两天内从 fork 到有完整 WebUI，这是客观事实。但问题是**每一轮用户验收都发现新 bug**，这说明我们缺乏"自测环节"。
- 10 个会议纪要记录了项目每一步决策，这个习惯很好。但我注意到纪要里的"下一步行动"经常没有被追踪到位——比如 Sprint3 规划里提到的"移动端适配"、"国际化"，后来就没人提了。

**方向看法：**

- 我认为现在最重要的一件事是：**定义 MVP 的完成标准**。用户嘴上说的"跑通全流程"，具体是什么？我建议明确：
  - [ ] 能在 WebUI 上创建一个定时任务（比如每天 8 点采集微信）
  - [ ] 定时任务到点自动执行采集
  - [ ] 采集结果自动推送到飞书多维表格
  - [ ] 能在飞书看到数据
  - 这 4 步全跑通 = MVP 完成
- MVP 完成之前，不建议做任何新平台搜索、新功能、国际化等。

**Ideas：**

1. **用户验收清单**：编写一份可勾选的端到端测试清单，交给用户按步骤走一遍
2. **版本号管理**：现在 dev 分支有 66,000 行增量但没有版本号。建议在 MVP 完成时打 tag v0.1.0，作为第一个里程碑
3. **Changelog**：用户部署到服务器后，需要知道自己的版本和变更内容

### Researcher（技术调研员）

**当前状态评估：**

- 从技术调研角度，这个项目的外部依赖风险比较集中：**wechat-article-exporter** 是唯一的微信数据源，auth key 4 天过期，而且是第三方服务。如果用户部署到服务器上，这个 key 过期后需要到本地浏览器重新获取——这对"自动化"是个根本矛盾。
- 小红书的 HTTP 直接抓取（不走 Playwright）受反爬限制严重。之前实现的 `_xhs_fetch_profile` 用 httpx 直接 GET 个人主页，小红书大概率会返回空白或 403。实际可靠的方式还是得走 Playwright 签名。

**方向看法：**

- 部署到 Linux 后，Playwright 浏览器占用约 400-500MB 内存。如果只是跑微信模块（不需要 Playwright），可以做到轻量部署。但一旦要支持小红书/抖音/B站爬虫，Playwright 是必须的，服务器配置要求会上来。
- 建议用户明确"服务器上要跑哪些平台"，这直接影响资源规划。

**Ideas：**

1. **微信 auth key 自动刷新调研**：能否通过 headless 浏览器自动化登录 wechat-article-exporter 来刷新 auth key？这样才能真正实现"全自动"
2. **平台分级**：把平台分为"轻量级（纯 HTTP API）"和"重量级（需要 Playwright）"两类，让用户在部署时选择需要的平台，按需安装浏览器
3. **爬虫健康监控**：定时检查各平台 API 是否可达，auth 是否有效，在 Dashboard 上显示"平台健康状态"

### Profile-Designer（UI/交互设计）

**当前状态评估：**

- WebUI 目前用 Naive UI 组件库，功能完整但**信息密度偏高**。以订阅管理页为例，搜索区域 + 提示 + 表格 + 分页一屏展示，新用户第一次进来可能不知道从哪开始。
- 配置管理页的表单很长（飞书、微信、各平台配置全在一起），缺乏**引导感**。用户不知道哪些是必填的、配置后需要做什么。

**方向看法：**

- 如果目标用户是"非技术人员"，当前 UI 还不够友好。但如果目标用户是"懂一点技术的运营人员"，现在的 UI 基本够用，只需要在**引导流程**上做优化。
- 不建议现在做大的 UI 重构。但有几个低成本高回报的改善。

**Ideas：**

1. **首次使用引导（Onboarding Wizard）**：第一次打开 WebUI 时，弹出简单的 3 步引导：① 配置数据源 → ② 添加订阅 → ③ 创建定时任务。用 Naive UI 的 Steps 组件就行
2. **Dashboard 健康面板**：目前 Dashboard 比较空。加一个"系统健康"卡片——显示各平台连接状态（绿/黄/红灯）、上次采集时间、飞书同步状态。用户一眼就知道系统是否正常
3. **配置分组折叠**：配置管理页按平台分组折叠，默认折叠，只展开用户实际使用的平台
4. **移动端**：暂时不做，但 Naive UI 的响应式能力不错，如果后续需要，Grid 布局调整一下就行

### Code-Reviewer（代码质量）

**当前状态评估：**

- dev 分支 66,000 行增量、零测试覆盖（之前的 smoke test 只跑了一轮后没有维护）。这是最大的技术债。
- `mypy.ini` 存在但没有在 CI 中跑。我本地跑了一下 `mypy api/`，有不少 type hint 缺失的 warning。
- 代码风格不够一致：有的文件用 `from config import wechat_config`，有的直接 `import config`；有的用 `httpx.AsyncClient`，有的用 `aiohttp`（虽然后者现在可能已经移除了）。
- `except Exception: pass` 模式在代码中反复出现，这是"隐藏 bug 的温床"。上一轮修的测试连接假阳性就是这个原因。

**方向看法：**

- **在合并到 main 之前，至少做到**：
  1. 关键路径有集成测试（配置保存 → 热重载 → 搜索 → Pipeline 执行）
  2. 消除所有 `except Exception: pass`（改为具体异常 + logging）
  3. mypy 至少在 service 层通过
- 不要求 100% 覆盖率，但"用户会实际走到的路径"必须有测试。

**Ideas：**

1. **GitHub Actions CI**：添加 `.github/workflows/ci.yml`，跑 `pytest` + `mypy` + `ruff format --check`。每次 push 自动检查
2. **异常处理规范**：制定一个规则——所有的 `except` 必须指定具体异常类型，必须有 `logger.warning/error` 记录，禁止 `pass`
3. **dev → main 合并检查清单**：在合并前走一遍代码审查，至少确保没有硬编码的密钥（`.env` 里的 key 不能出现在代码里——我注意到 `wechat_config.py` 里硬编码了一个默认 auth key `"3a7a1612d29f479ea2f3647a4640544e"`，这应该改成空字符串）

## 三、自由讨论

### 讨论 1：配置系统是否需要重构？

**Dev**：我觉得这是当前最大的技术风险。两套配置读取机制一定会再出 bug。  
**Code-Reviewer**：同意。但大重构现在不合适，用户等着跑通全流程。  
**Brain**：折中方案——不做大重构，但在 `config_service` 里加一个 `get(key)` 方法作为统一入口，新代码全部走这个入口，旧代码逐步迁移。  
**共识**：✅ 采纳折中方案。不立即重构，但新代码必须通过 `config_service.get(key)` 读取配置。

### 讨论 2：MVP 的范围怎么定？

**PM**：我刚才提了 4 步清单，大家觉得合适吗？  
**Dev**：基本同意，但要补一条：「采集结果能在数据浏览页看到」——这证明数据确实入库了。  
**Researcher**：还有一条：「定时任务执行历史能在 WebUI 上看到日志」——这是用户信任系统的基础。  
**PM**：好，更新为 6 步：① 创建定时任务 → ② 到点自动执行 → ③ 采集结果入库可见 → ④ 推送飞书可见 → ⑤ 执行日志可查 → ⑥ 整个过程无需人工干预  
**共识**：✅ MVP = 这 6 步端到端跑通（微信平台优先，因为最成熟）

### 讨论 3：部署策略——Docker 还是直接部署？

**Researcher**：Docker 镜像因为包含 Playwright 浏览器会很大（约 1.5-2GB）。如果只跑微信模块不需要 Playwright，直接 `uv run` + systemd 更轻量。  
**Dev**：Docker 的好处是环境一致性。但是 Playwright 在容器里跑确实有坑（字体、沙盒、共享内存）。  
**Profile-Designer**：从用户体验来看，`docker-compose up -d` 一条命令启动是最简单的。  
**Brain**：建议两条路都保留。Dockerfile 已经有了，systemd service 也有了。文档里写清楚「轻量部署（仅微信/API）用 systemd」、「全功能部署用 Docker」。  
**共识**：✅ 双轨策略，文档区分场景。

### 讨论 4：关于 wechat-article-exporter 的外部依赖

**Researcher**：auth key 4 天过期是个硬伤。用户部署到服务器后没有浏览器环境，怎么刷新 key？  
**Dev**：理论上可以在服务器上跑 headless 浏览器自动登录，但微信那边会反爬。  
**Brain**：这个暂时无解。先在文档里明确告知用户这个限制，并在 Dashboard 上显示 auth key 的健康状态（过期倒计时 / 最后一次验证成功时间）。  
**共识**：✅ 短期靠提示，中期调研自动刷新可能性。

### 讨论 5：代码硬编码的 auth key

**Code-Reviewer**：`wechat_config.py` L57 硬编码了 `"3a7a1612d29f479ea2f3647a4640544e"` 作为默认值。这个 key 已经泄露在 git 历史里了。  
**Dev**：这是开发时为了方便填的。应该改成空字符串。  
**Brain**：同意，推到代码上去。也在 `.env.example` 里加说明。  
**共识**：✅ 立即修复。
