# 内部规划研讨会纪要
**日期：** 2026-03-01  **主持人：** 高级产品技术顾问  **参与角色：** PM / BE / FE / OPS

---

## 开场

> 系统核心功能已全部交付，今日三个痛点修复完成，进入稳定运营阶段。本次会议聚焦"下一步优化方向"，请各角色直接说建议，不做铺垫。

---

## 一、产品经理（PM）发言

1. **新用户零配置上手**：目前配置向导步骤繁多，新用户第一次跑通全流程平均需要 30 分钟以上。应提供"快速开始"模板（预填常见场景参数），一键导入即可试跑。
2. **任务模板库**：用户高频重复配置相同 Pipeline，建议支持"另存为模板"并在新建任务时选择，降低重复劳动。
3. **执行结果摘要卡片**：日志全量输出对非技术运营不友好，任务完成后应在 WebUI 展示"推送 N 条 / 跳过 M 条 / 失败 K 条"的摘要卡片，而非让人翻日志。
4. **多飞书空间支持**：目前凭证是全局单一配置，有用户同时维护多个飞书企业，需要按任务级别切换凭证。
5. **移动端基础可读性**：运营经常在手机上查看任务状态，当前 WebUI 在移动端几乎不可用，至少做响应式查看（不需要编辑）。

---

## 二、后端工程师（BE）发言

1. **子进程改造为 in-process 执行**：当前 Pipeline 步骤使用 subprocess 拉起子进程，Windows 兼容问题是今日刚修的坑，根本上应重构为 async 函数调用或线程池，彻底消除跨进程的环境依赖。
2. **SQLite snapshot 加锁 + 过期清理**：多任务并发时 `feishu_record_snapshot` 存在写冲突风险，需加行级乐观锁；同时历史快照无限增长，需加 TTL 自动清理机制。
3. **统一错误码体系**：各步骤抛出的异常类型不一，前端无法区分"网络超时"和"字段不存在"。建立 `CrawlerError(code, message, retryable)` 统一错误结构，支持前端针对性提示和自动重试。
4. **增量同步防重复**：feishu_pull 每次全量拉取，数据量大时耗时且浪费 API 配额。应引入基于 `last_modified_time` 的增量拉取策略。
5. **可观测性**：添加 Prometheus metrics 暴露（任务成功率、步骤耗时 P95），方便后续接入 Grafana 监控。

---

## 三、前端工程师（FE）发言

1. **任务执行实时日志流**：当前日志需手动刷新，应改为 SSE 或 WebSocket 实时推送，任务执行期间流式渲染日志，有"正在执行第 N 步"的进度感知。
2. **Pipeline 步骤可视化编排**：步骤配置目前是纯表单，顺序不直观。改为拖拽式流程图（节点连线），让用户一眼看清数据流方向，也更易发现配置错误。
3. **字段映射交互优化**：字段映射当前是两列文本输入，容易填错。应改为从飞书表实时拉取字段列表，提供下拉选择 + 自动匹配建议。
4. **暗色模式**：Naive UI 原生支持，工程量小，但运营反馈强烈要求，做了用户满意度立竿见影。
5. **操作结果 Toast 统一化**：当前部分操作有 Toast 反馈，部分没有；错误提示有时只在控制台。需统一所有操作的成功/失败反馈规范。

---

## 四、运营/用户代表（OPS）发言

1. **任务失败自动通知**：任务在夜间定时跑失败了，第二天才发现数据没同步。需要支持飞书机器人/邮件失败告警，指明哪个步骤出了什么问题。
2. **历史执行记录可查**：目前只能看"最近一次"日志，想回溯 3 天前某次任务失败原因，翻不到。需要保留最近 N 次执行历史（含状态、时长、日志快照）。
3. **手动触发单步骤重跑**：Pipeline 前三步成功、第四步因网络抖动失败，目前只能整条重跑。希望能从失败步骤断点续跑，节省时间和 API 配额。
4. **字段映射配置可导出/导入**：不同任务之间字段映射大量重复，每次都要手动填。能否导出 JSON 配置在任务间复用？
5. **飞书表二数据预览**：推送前能不能先看一眼"将要写入的数据长什么样"，而不是推出去再去飞书检查，Dry-run 模式已有但结果只在日志里，不够直观。

---

## 主持人总结

### Top 6 优化方向（综合价值 × 可行性排序）

| # | 方向 | 一句话描述 | 工作量 |
|---|------|-----------|--------|
| 1 | **任务失败实时告警** | 飞书机器人推送失败详情，运营第一时间感知 | **S** |
| 2 | **执行历史记录 + 断点续跑** | 保留最近 30 次执行快照，支持从失败步骤恢复 | **M** |
| 3 | **日志实时流式推送（SSE）** | WebUI 执行期间流式渲染日志，告别手动刷新 | **S** |
| 4 | **子进程 → in-process 重构** | 彻底消除 subprocess 跨平台兼容隐患，提升稳定性 | **M** |
| 5 | **任务模板 + 快速开始** | 常见场景一键套用，新用户上手时间从 30 分钟降至 5 分钟 | **M** |
| 6 | **字段映射下拉选择 + 导入导出** | 从飞书实时拉取字段供选择，配置可复用，减少手填错误 | **M** |

### 可并行推进的组合

- **并行 A**：`#1 失败告警` + `#3 日志实时流`——两者均为独立的通知/IO 模块，无代码依赖，可同时开发。
- **并行 B**（第二阶段）：`#4 in-process 重构` + `#5 任务模板`——一个纯后端、一个产品功能，互不阻塞。
