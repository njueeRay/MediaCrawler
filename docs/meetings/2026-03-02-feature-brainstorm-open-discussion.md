## 议题一：AI 内容分析层 —— 让爬到的数据「会说话」

**【Brain】** 我一直觉得我们系统现在有个很大的浪费：8 个平台爬了那么多内容，最后躺在 SQLite 或飞书表格里，用户还得自己去看、自己去筛。这就是个数据仓库，不是数据产品。

我想聊的是接入 LLM，做内容智能分析层。具体来说，爬完内容之后，自动跑一遍：情感判断（正负中）、话题分类、关键词提取、摘要生成，结果写回数据库，飞书同步时带上这些字段。

**【Researcher】** 这个需求我有强感知。我帮几个甲方做竞品监控，他们最痛的不是爬不到数据，是爬到了看不过来。一个账号一天发 10 条，你追踪 50 个账号，就是 500 条，靠人肉过滤根本不现实。他们现在要么付费用第三方情报工具，要么自己写脚本。如果我们内置这个能力，差异化就出来了。

**【Dev】** 技术方向上有几个路子。最简单的是接 OpenAI / DeepSeek API，爬完之后异步跑一个 enrichment job，把文本送过去，结果写回一个 `content_analysis` 字段或者单独的分析表。这个成本不高，我估计数据库加个表、pipeline 加个 `AIEnrichStep`，一周内能出原型。

复杂点的是本地模型。用户如果数据量大、不想把内容发到外部，可以跑 Ollama，我们接 Ollama HTTP API，对外暴露一样的接口，内部可切换。

**【Code-Reviewer】** 我有几个顾虑。第一，API 限流——如果一次爬 1000 条，你要批量送给 LLM，OpenAI 有 TPM 限制，得做并发控制 + 重试 + 背压。第二，成本——用户不一定清楚 LLM 是按 token 计费的，如果我们没有明确的「分析开关」和「费用预估提示」，用户一不小心跑了大批量，账单来了会骂我们。第三，结果质量——情感分析在垂类内容（美妆、二次元）上准确率并不高，我们有没有办法让用户校正或者设置 prompt 模板？

**【Dev】** 这些都不是不能做，但确实要加工程保护。限流我们用 token bucket 或者信号量控一下并发数；费用提示加在 UI 里，配置项里要求用户填 API Key 的时候顺便显示「本次预估消耗 X tokens」；Prompt 模板可以做成可配置的，放在数据库里，用户可以自定义。

**【Brain】** 我再加一层商业视角：这个能力如果做好了，是可以作为付费订阅功能的「锚点」的。免费版不带 AI 分析，Pro 版带，这就是 SaaS 分层的典型逻辑。

**【PM】** 好，初步结论：**AI 内容分析层**是高价值方向，技术可行，但工程保护要到位。进入候选列表，标记为「P1·中长期」。落地分两步：先做 OpenAI 接入的 `AIEnrichStep`，再做 Ollama 后端切换。

## 议题二：多账号管理 + Cookie 池 —— 让爬虫更持久

**【Dev】** 我来开这个话题。目前系统最大的脆弱点之一是每个平台只有一个 Cookie/账号。一旦被封或者过期，整个爬虫就停了。我们现在小红书和微信公众号都有这个问题，C-04 里专门有「微信 Cookie 自动刷新」。

但这只是治标。根本方案是**多账号池**——数据库存多个账号，爬虫执行前自动从池里挑一个可用的，失败了就换下一个，同时标记当前账号为「冷却中」。

**【Researcher】** 这个用户会爱死的。我见过很多人为了维持 Cookie 有效性，专门开着浏览器模拟人工浏览，甚至买了好几个小号轮流用。如果系统能自动管理，减少的人工成本非常直接。

**【Brain】** 账号管理这个方向有个商业化延伸：代理 IP 池。我们现在 `proxy/` 模块是有基础的，但 UI 上完全不可见。如果账号池 + 代理池都做出来，打包成「反封禁套件」，那就是企业版很自然的卖点。

**【Code-Reviewer】** 我要说几个硬约束。第一，账号信息（Cookie、密码）是高敏感数据，必须加密存储，不能明文写数据库——这跟 S-03「敏感配置加密」得联动。第二，多账号并发可能触发平台的「异地登录」检测，一个 IP 上用不同账号反而更容易被封；账号和代理要做绑定，一个账号只走同一个出口 IP，这个逻辑不简单。第三，账号「健康度」怎么检测？是靠爬虫失败反推，还是定期主动探针？探针会不会本身就消耗请求配额？

**【Dev】** 这些都是真实挑战。我设想的数据模型是这样：`PlatformAccount` 表存账号基本信息+加密 Cookie + 绑定 proxy_id + 状态（active/cooldown/banned）+ 失效时间。爬虫执行层有个 `AccountSelector` 服务，按平台+优先级选账号，执行完更新状态。探针就做个轻量的「登录态检查」接口，定时任务每 4 小时跑一次，失败就触发告警。

**【PM】** 这个方向工程量不小，但价值明确。**多账号 + Cookie 池管理**进候选列表，标记「P1·中期」。依赖 S-03 加密存储，需要联动 C-03 CrawlerPool 重构。

## 议题三：数据可视化 Dashboard —— 从「数字」到「洞察」

**【Researcher】** 我想聊这个，因为用户反馈里出现频率最高的不是「爬不到」，是「不知道爬了什么」。现在的 Dashboard 只有健康面板，告诉你系统有没有挂，但没有告诉用户：这周爬了多少条？哪个平台产量最高？最近的爬取失败率趋势是什么？有没有某个账号突然沉默了？

**【Brain】** 这个我完全同意，而且我想扩大范围。不只是系统运营数据，还有**内容数据的可视化**。比如：我追踪的 50 个账号，这周发帖量对比；某个关键词在不同平台的声量变化；热门内容的互动率分布。这就从「爬虫管理工具」变成了「内容情报平台」了。

**【Dev】** 这在技术上分两层。第一层是**运营指标**，数据都在我们的 `TaskExecution` 和 `SyncHistory` 表里，做个聚合查询 + ECharts 就能出来，W-05 里已经有这个坑位。第二层是**内容指标**，需要对爬到的内容做统计——这得有个专门的统计表或者物化视图，不然每次 Dashboard 加载都全表扫描，性能会很惨。

**【Code-Reviewer】** 正是，数据量大了以后，Dashboard 查询是个性能陷阱。我建议统计数据要分开算——要么用数据库触发器/定时任务维护汇总表（`daily_stats`），要么用后台 job 定期跑聚合写缓存，frontend 只读缓存结果，绝对不能在 API 请求时实时全表扫。另外，如果未来要做「内容指标」，爬虫模型里的互动数（点赞、评论数）字段要统一——现在 8 个平台的 model 字段名都不一样，先统一 schema 才能做跨平台统计。

**【Researcher】** 用户还有个很真实的需求：**下载/导出报告**。每周一份 PDF 或者 Excel，告诉他「上周我追踪的 A 品牌在小红书有多少条提及，前三热帖是什么」。这对汇报给老板的内容运营人员特别有用。

**【PM】** 好，这个话题分两层落地。**运营 Dashboard 增强**（W-05 延伸）入候选列表，算「P1·近期」，工程量不大。**内容数据可视化 + 报告导出**是更大的方向，入候选列表标「P2·中期」，依赖 schema 统一和统计表设计。

## 议题四：Webhook/回调 + 第三方集成生态

**【Brain】** 现在系统的输出端只有飞书。但用户的工作流远不止飞书——有用 Notion 的、用 Airtable 的、用企业内网 ERP 的。我们要不要做一个**通用 Webhook 机制**：爬取完成/分析完成/同步完成这些事件，自动向用户配置的 URL 发一个 HTTP 回调，带上结构化数据？这样任何能接 Webhook 的工具都能对接。

**【Dev】** Webhook 这个本身不难做。在 Pipeline 执行完成的事件节点，读取用户配置的 Webhook URL，异步发一个 POST。技术上就是 `httpx.AsyncClient` 发请求，加重试，失败记日志。数据结构用我们现有的 Pydantic schema 序列化。一两天能出原型。

稍微复杂一点的是**签名验证**——Webhook 业界标准是在 Header 里带 HMAC-SHA256 签名，接收方可以验证这条消息确实来自我们，不是别人伪造的。这个要做，是安全基本功。

**【Code-Reviewer】** Webhook 有几个运维噩梦点：一是接收方挂了怎么办？需要有重试策略（指数退避）+ 死信队列，不能一次失败就扔掉；二是我们能不能控制并发出去的 Webhook 数量，别把用户的服务器打挂；三是要有一个「Webhook 发送历史」页面，让用户能看到每次触发的结果（成功/失败/响应码），方便他们调试。这些加起来其实也不少工程量。

**【Researcher】** 我觉得比通用 Webhook 更有价值的是**原生集成**。飞书是因为我们有人工作在飞书生态里，所以做得深。但国内用钉钉、企业微信的用户同样多。能不能把飞书推送这条路复制一份给企业微信和钉钉？API 结构是类似的，主要是适配器层的工作。

**【Dev】** 企业微信/钉钉的群机器人消息推送确实很简单，能一两天原型出来；但如果要做到飞书多维表格那种「写入结构化数据」级别，两者的 API 差异就大了。企业微信没有类似飞书多维表格的产品，钉钉有「智能表单」但 API 文档一言难尽。我建议分两级做：轻量通知（新内容到了发消息）走 Webhook，深度结构化存储还是飞书专属。

**【Brain】** 这个拆法合理。不同的有效触达场景对应不同深度的集成。

**【PM】** 结论：**通用 Webhook 机制**进候选，标「P2·中期」，需要安全签名 + 重试 + 发送历史。**企业微信/钉钉群通知**（轻量）进候选，标「P3·较低优先」，场景是「通知有新内容」而非「写入数据」。

## 议题五：增量爬取 + 智能调度 —— 别浪费资源

**【Dev】** 这个话题我有很强的动力聊，因为现在的调度是「定时全量爬」，非常粗暴。比如我设了每 2 小时爬一次某账号，但有些账号一周才发一次帖，每 2 小时跑一次完全是浪费；反过来，有些账号搞活动时一天发 10 条，2 小时的间隔又太慢。

我想做的是**自适应调度**：根据账号历史发布频率，动态调整爬取间隔。发帖频繁的账号，间隔自动缩短；沉默账号，间隔自动延长，直到有新内容才恢复高频。

**【Researcher】** 这个用户会觉得「系统好像聪明了」，体验提升感非常强。还有一个相关需求：**增量去重**。用户现在最怕的是爬到重复内容，飞书表格里一堆重复行，他们自己要手动去删。如果每次爬完能自动对比「这条内容上次有没有爬过」，只推送新内容，那就完美了。

**【Brain】** 增量爬取是「让用户续费」的核心功能之一。用户初期试用时是全量爬，感觉爽；但用了三个月发现每次都是重复数据、账单却在涨，就会觉得「这东西太贵了」。如果我们能做到「只爬新的」，ROI 一下子就拉高了。

**【Code-Reviewer】** 实现上要区分「增量」的粒度。内容 URL 级别的去重比较简单，给 `content_id`（各平台的原生 ID）加唯一索引，插入时 ON CONFLICT IGNORE，之前已经爬过的就跳过。但是「内容是否被更新」就复杂了，比如一篇笔记昨天没点赞，今天突然爆了几千赞，要不要重新同步？这个「更新检测」逻辑需要跟用户讲清楚，不能默认做，因为会引入频繁的 diff 操作。

自适应调度更复杂，你得有个「账号发布节奏」的历史数据支撑，还要处理假阳性——账号停更了但我以为是正常，然后把间隔调成 7 天，结果账号复活发帖，我 7 天后才发现，用户会骂的。

**【Dev】** 对，自适应调度要有个「最大间隔上限」，不管多久没发帖，爬取间隔不超过 24 小时。具体实现上，APScheduler 支持 `date_modified_interval` 这种动态 trigger，我们可以在每次任务执行完后，根据本次结果更新下次触发时间——这比改 cron 表达式灵活多了。

**【PM】** **增量去重**（基于 content_id 唯一索引）入候选，标「P1·近期」，工程量小，价值大。**自适应调度**入候选，标「P2·中期」，依赖「账号发布节奏」统计，有冷启动问题，需要设计仔细。

## 议题六：内容关键词追踪 + 媒体监控模式

**【Researcher】** 现在订阅维度是「账号」——我追踪某个达人。但很多用户的需求不是追人，是**追话题**。比如品牌方想知道「有没有人提到我家产品」，公关想监控「行业里有没有出现负面舆情」，这本质上是关键词订阅，不是账号订阅。

现在我们的爬虫有「搜索模式」和「博主详情模式」，搜索模式已经可以按关键词爬了，问题是没有持久化的「关键词订阅」概念。

**【Brain】** 这是一个典型的**舆情监控**场景，这个市场已经有专门的付费产品（如识微商情、新榜、清博等），收费几千到几万一年。我们做出来可以打低端价位，对独立开发者和小团队非常有吸引力。关键差异是：我们是自托管的，**数据不出用户的服务器**，这对合规敏感的用户是比功能更大的卖点。

**【Dev】** 技术上，「关键词订阅」其实只是 `Subscription` 表的一种新的 `subscribe_type`，目前是 `creator`（创作者），新增 `keyword` 就好。爬虫执行层，对 `keyword` 类型订阅，调用各平台的 search API，结果过滤后和正常 `creator` 类型走同一条后续流程。数据库层需要一个「命中关键词」字段，方便后续过滤。

难的是**多平台关键词搜索的 API 差异**。小红书要模拟搜索请求，抖音有搜索 API，B站搜索结果页结构经常变，快手搜更不稳定。每个平台的搜索接口都要单独适配、单独维护。

**【Code-Reviewer】** 还有一个去重维度的问题：同一条内容可能被多个关键词命中（比如帖子同时包含「iPhone 15」和「苹果手机」两个词组），要防止重复入库、重复通知用户。建议在关键词匹配结果写库前做内容 ID 去重，而不是依赖关键词维度去重。

**【Researcher】** 对，用户对这类工具还有个高频需求：**告警**。关键词出现了，立刻通知我（钉钉/邮件/企业微信）。这跟 Webhook 议题可以串起来——关键词命中 → 触发 Webhook → 推送通知。

**【PM】** 这个议题有很好的联动性。**关键词订阅模式**入候选，标「P1·中期」，依赖 `Subscription` 表扩展 + 各平台 search 接口适配。**关键词告警**依赖 Webhook 机制，联动议题四。

## 议题七：SaaS 多租户 —— 走向商业化

**【Brain】** 我们在 v1.3 要做 JWT 认证了，这其实是走向多用户的第一步。但真正的商业化需要的是**多租户**：不同的用户有自己的数据隔离空间，有自己的订阅、任务、飞书配置，互相不可见。一个 SaaS 产品，你在上面开不同的账号，每个账号的数据独立。

这个做到以后，我们可以做云端托管版——用户不需要自己部署，开一个账号就能用，按月付费，每个月有爬取配额。

**【Dev】** 多租户是架构级改造，不是加几个字段就行的。首先，所有的数据表都需要加 `tenant_id`；其次，所有的查询都必须带 `tenant_id` 过滤（这是安全硬要求，漏了一个地方就是数据泄露）；第三，爬虫执行是单机进程隔离还是容器隔离？如果多租户在同一个 Python 进程里跑，理论上是可以的，但一个租户的失控爬虫会影响其他租户。

云端托管版的话还有合规问题——你存了用户数据，你的服务器上跑着他们的 Cookie，一旦出事，法律责任是你的。

**【Code-Reviewer】** 多租户的测试复杂度会爆炸。原来你写一个 pytest fixture 建一个用户，现在要建两个租户，测试每个查询在租户隔离下都正确。每个 API endpoint 都要有越权测试（租户 A 能不能访问租户 B 的数据）。这个 QA 成本不小。

**【Researcher】** 真实用户里，有多少人有多租户需求？我觉得 90% 的用户就是自己用或者团队内部用，他们需要的是「多用户共享一个系统」，而不是「数据完全隔离的多租户」。软一点的解法是做**团队工作区 + 角色权限**：一个 workspace 下可以有多个成员，管理员能看所有，普通成员只能看自己创建的任务，这个工程量比多租户小得多，但覆盖了大部分团队协作场景。

**【Brain】** 好，这个分层有道理。近期目标是「团队工作区 + RBAC」，中长期才是真多租户。

**【PM】** **团队工作区 + 角色权限（RBAC）**入候选，标「P2·中期」，依赖 S-01/S-02 JWT 认证 + API Key 完成后。**真多租户架构**入候选，标「P3·长期·架构级」，需要专项立项讨论，不进近期规划。

## 议题八：爬虫插件化 + 社区生态

**【Brain】** 最后一个议题，也是最激进的。现在新增一个平台爬虫要改多少文件——`media_platform/` 加目录、`model/` 加模型、`store/` 加存储、`config/` 加配置、`pipeline_steps.py` 加步骤……这个成本对贡献者来说太高了，导致开源社区很难有有意义的 PR。

如果我们做一个**爬虫插件化接口**——定义一个标准的 `Platform` 抽象，第三方只要实现这个接口，放到 `plugins/` 目录，重启服务就自动被发现和注册，不需要改核心代码——那我们的平台数量就不止 8 个了，社区可以贡献 Twitter、Telegram、Reddit，甚至企业内网论坛的爬虫。

**【Dev】** 想法非常好，但核心挑战是**接口设计的稳定性**。一旦我们把插件接口发布出去，升级它就是 Breaking Change，社区的插件全都要改。所以接口必须设计得足够抽象，又足够实用，这需要前期投入大量的设计工作，不能急着做。

技术路线上，Python 有成熟的插件机制——`entry_points`（setuptools）或者直接扫插件目录动态 `import`。我们用后者更轻量，不需要每个插件都打包成 pip package。插件实现一个 `AbstractCrawler`（现在已经有了），再加一个元数据 manifest（平台名、平台 ID、支持的步骤类型），系统启动时扫 `plugins/` 目录，自动注册到 `platform_registry`。

**【Code-Reviewer】** 插件化的安全风险不小。插件代码是任意 Python，意味着任何能访问你文件系统的人都能写一个「爬虫」来做坏事。在自托管场景下，用户是自己的管理员，这个风险用户自己承担。但如果未来做云端托管版，绝对不能让用户上传任意 Python 代码跑在服务器上——这就是远程代码执行漏洞。

**【Researcher】** 社区生态这件事，光有技术还不够，得有示范性插件。如果我们自己做一两个高质量的社区平台插件（比如 Reddit 或 Telegram），写好文档，社区才有参考。没有范例，很难有人跟进。

**【Brain】** 这是中长期的生态战略，急不来。但架构层面的「支持未来成为插件化系统」是可以尽早考虑的——不是现在全部改，而是在做 P-02「Pipeline 步骤注册表」的时候，顺手把平台注册也做类似的抽象。这是以小成本保留未来可能性的做法。

**【PM】** **爬虫插件化接口**入候选，标「P3·长期·需专项设计」，近期不启动但要在架构演进时意识到。**架构层面预留可插拔槽位**作为 P-02 的附加设计要求，加入下次 Sprint 规划的设计讨论议程。

## PM 最终结论

### 近期推荐优先项（v1.4 可纳入讨论）

这几项价值高、工程量可控，且与 v1.3 任务无冲突，建议下次规划会重点审视：

1. **SCH-01 增量去重** —— 几乎零架构成本，立刻降低用户数据噪音，强烈推荐。
2. **VIZ-01 Dashboard 增强** —— W-05 已有坑位，补完收益明显。
3. **WH-01 + WH-02 Webhook 机制** —— 打通集成生态的基础，后续 KW-02 依赖它。
4. **AI-01 AI 内容分析层** —— 差异化关键，原型可以小步快走，先做 OpenAI 单接入。

### 中期战略重点（v1.5-v2.0）

这些是真正拉开产品差距的方向，需要较多设计投入：

- **KW-01/KW-02 关键词订阅 + 告警**：定义产品从「爬虫工具」到「内容情报平台」的转折点。
- **ACC-01/ACC-02 多账号管理**：解决爬虫稳定性的根本问题，商业化支撑。
- **VIZ-02/VIZ-03 内容可视化 + 报告导出**：提升向上汇报/汇报场景的用户依赖度。

### 长期架构方向（需专项论证）

- **RBAC + 多租户**：在无明确 SaaS 计划前克制推进，先把团队协作场景做好。
- **插件化生态**：架构层提前预留抽象，等社区活跃度到达拐点再正式推。
